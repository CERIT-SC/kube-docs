**JupyterHub** at CERIT-SC provides researchers and scientists with instant, browser-based access to interactive computing environments (JupyterLab, RStudio, MATLAB, and VS Code) backed by high-performance CPU and GPU resources.

To accelerate your research, our platform features **built-in, on-premise Generative AI assistants** (Jupyter AI, Claude Code, and Posit Assistant). Because our Large Language Models (LLMs) run entirely on CERIT-SC infrastructure, **your unpublished research data, sensitive datasets, and proprietary code never leave our servers.

## 1. Quick Start: Launching Your Environment

To access JupyterHub, you must have an active **MetaCentrum** account.

1. Log in at **[hub.cloud.e-infra.cz](https://hub.cloud.e-infra.cz/)**.
2. **Quick Launch:** Click **`My Server`** to start a default environment immediately.
3. **Custom Launch (Recommended):** To run multiple environments or customize your setup, enter a short, descriptive name under **Add new server** and click the button to configure your instance.

## 2. Configuring Your Server

When spawning a new server, you will configure three main components: your **Software Image**, **Storage**, and **Hardware Resources**.

### Step A: Choose Your Image
Select a pre-configured environment tailored to your scientific domain:

| Category | Image Options | Best For |
| :--- | :--- | :--- |
| **AI-Enhanced Python / Data Science** | `Minimal NB AI`, `DataScience NB AI` | General data analysis, Python coding with built-in **Jupyter AI** chat and **Claude Code** agentic assistant. |
| **Statistical Computing (R)** | `RStudio-AI` (`4.6.1`), `cerit.io/hubs/rstudio:4.5.2-ai` | R programming with **Posit Assistant** or **Claude Code** integration. |
| **Machine & Deep Learning** | `TensorFlow`, `PyTorch` (look for `...with GPU...`) | Training neural networks and GPU-accelerated calculations. |
| **Structural Biology** | `Folding images` (ColabFold / ESMFold) | Protein structure prediction and bioinformatics. |
| **Engineering & Math** | `Matlab` | Interactive, full graphical MATLAB desktop environment in your browser. |
| **Remote Development** | `Minimal NB with SSH access` | Connecting your local IDE (e.g., local VS Code or PyCharm) via SSH. |

> **Using a Custom Docker Image:** You can supply your own public Docker image in the format `repo/imagename:tag` (e.g., hosted on Docker Hub or the [CERIT-SC Harbor registry](../docker/harbor)). Always build on top of an [existing Jupyter Docker Stack image](https://jupyter-docker-stacks.readthedocs.io/en/latest/using/selecting.html) to ensure all required JupyterHub startup scripts are present.

![JupyterLab Launcher](/img/ceritsc/apps/jupyterhub/lab.png)

### Step B: Configure Storage
* **Default Persistent Storage (`/home/jovyan`):** Every notebook automatically mounts a persistent disk at `/home/jovyan` (or `/home/rstudio` in RStudio). **Always save your scripts and results here** so they persist when your server stops. You can also reuse and share this storage across different notebook instances.
* **MetaCentrum Home (`/home/meta/<username>`):** You can mount one MetaCentrum storage home or project directory per notebook to access your existing grid files directly.

<Callout type="warning">
**Prevent Spawn Failures:** Only select a MetaCentrum storage location where you actually have an existing home directory. Selecting an uninitialized storage location will cause your server startup to fail.  If you are not sure about home location, contact <a href="mailto:k8s@cerit-sc.cz">IT Service desk</a> who will help.
</Callout>


### Step C: Allocate Hardware Resources (CPU, RAM, GPU)
Request only what your current workflow requires:
* **CPU (Guaranteed: 1 | Max: 32):** Soft-handled. If your code exceeds your CPU limit, your notebook **will not crash**—the computation will simply be throttled (run slower).
* **RAM / Memory (Guaranteed: 4 GB | Max: 256 GB):** Hard limit. **Warning:** If your code consumes more RAM than allocated, the kernel/process will be abruptly terminated (Out-Of-Memory error), though your notebook interface will stay open.
* **GPU (Whole GPU or NVIDIA MIG Slices):**
  * **Whole GPU:** Only select a GPU if you are also selecting a GPU-enabled image (marked with `...with GPU...`), which includes the necessary CUDA drivers.
  * **NVIDIA MIG (Multi-Instance GPU):** Ideal for smaller models or testing. You can request isolated hardware slices of an NVIDIA A100 (80 GB) card—up to 4 slices of `10GB part A100` or `20GB part A100`. Each slice acts as an independent GPU with dedicated memory. *(Note: Using more than 1 MIG slice requires multi-GPU support in your code).*

### Managing Custom Conda Environments
All images support `conda`. If you need specific library versions (e.g., `scanpy`, `biopython`, or a specific `scikit-learn`) that remain available across sessions, create a custom kernel:

1. Open a **Terminal** in JupyterLab and initialize Conda:
   ```bash
   conda init
   ```
2. Create a new environment. **Important:** You must include `ipykernel` and `nb_conda_kernels` (or `irkernel` for R) so Jupyter can see the environment:
   ```bash
   conda create -n bio_env --yes python=3.10 ipykernel nb_conda_kernels biopython scipy
   ```
   ![moveenv](/img/ceritsc/apps/jupyterhub/move_env.png)
3. Verify your environment is listed:
   ```bash
   conda env list
   ```
   ![checkenv](/img/ceritsc/apps/jupyterhub/check_env.png)
4. Install additional packages anytime with:
   ```bash
   conda install -n bio_env seaborn
   ```
5. Switch your notebook to the new environment via the top menu: **Kernel &rarr; Change Kernel...** and select `bio_env`.
   ![selenv](/img/ceritsc/apps/jupyterhub/select_env.png)

### Running Interactive Dashboards (Streamlit, Dash, Gradio) via Flare
If you build an interactive web app inside your notebook (such as a **Streamlit** data explorer, **Plotly Dash** app, or **Gradio** ML demo), you can expose it to a public URL using our `flare` tunnel tool:

1. In your Jupyter terminal, install `flare`:
   ```bash
   pip install git+[https://github.com/CERIT-SC/flare](https://github.com/CERIT-SC/flare)
   ```

2. Start your web application in the background (for example, a Streamlit app running on port `8501`):

   ```bash
   flare tunnel --port 8501 --name my-lab-dashboard
   ```

### Offloading Heavy Computations to Background Kubernetes Jobs
Jupyter notebooks are ideal for interactive exploration, but if you have a script that takes days to run or requires heavy resources, **offload it as a background Kubernetes `Job`**. This keeps your interactive notebook responsive and avoids holding onto large resource allocations unnecessarily.

#### Step 1: Set Up `kubectl` in Your Terminal
*(Note: For RStudio images, run these commands in the terminal to install and configure `kubectl`):*
```bash
# 1. Download kubectl (if curl is missing, run: fakeroot apt-get update && fakeroot apt-get install -y curl)
curl -LO "[https://dl.k8s.io/release/$(curl](https://dl.k8s.io/release/$(curl) -L -s [https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl](https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl)"

# 2. Install kubectl
fakeroot install -o rstudio -m 0755 kubectl /usr/local/bin/kubectl

# 3. Configure cluster environment variables
export KUBERNETES_PORT=tcp://10.43.0.1:443 KUBERNETES_PORT_443_TCP=tcp://10.43.0.1:443 \
       KUBERNETES_PORT_443_TCP_ADDR=10.43.0.1 KUBERNETES_PORT_443_TCP_PORT=443 \
       KUBERNETES_PORT_443_TCP_PROTO=tcp KUBERNETES_SERVICE_HOST=10.43.0.1 \
       KUBERNETES_SERVICE_PORT=443 KUBERNETES_SERVICE_PORT_HTTPS=443

# 4. Verify connection (should list your running notebook pods)
kubectl get pods
```

#### Step 2: Find Your Storage Volume Names (PVCs)
To let your background Job read your scripts and write output directly back to your notebook's folders, locate the `PersistentVolumeClaim` (PVC) names for your storage:

* **Find your Notebook Home PVC (`/home/jovyan` or `/home/rstudio`):**
  ```bash
  kubectl get pvc | awk -v volume=$(df -h | awk '$1 ~ /^147\.251\.6\.218:/ {split($1, a, "/"); print a[length(a)]}') '$3 == volume {print $1}'
  # Example output: testuser-home-pipemaster
  ```
* **Find your MetaCentrum Home PVC (`/home/meta/<username>`):**
  ```bash
  # 1. Check which MetaCentrum storage server is mounted:
  df -h | awk '$NF ~ /^\/home\/meta/ {match($1, /@([^:]+):/, m); print m[1]}'
  # Example output: storage-brno2.metacentrum.cz

  # 2. List your SSHFS claims and match the server name (e.g., brno2):
  kubectl get pvc | awk '$3 ~ /-data-sshfs$/ {print $1}'
  # Example output: testuser-brno2-claim
  ```

#### Step 3: Define Your Job
When creating your Kubernetes Job manifest, specify four items: (1) the **Docker image** containing your libraries, (2) the **command/script** to execute, (3) **CPU/RAM resources**, and (4) the **PVC volume mounts** discovered in Step 2 so outputs are written directly back to your notebook directory. *(Need help writing a Job manifest? Contact **k8s@cerit-sc.cz**).*

3. Inside the JupyterLab terminal, add your laptop's public SSH key (`~/.ssh/id_rsa.pub`) to `/home/jovyan/.ssh/authorized_keys`:

4. Verify that the `sshd` daemon is running using `ps -fax`. If you do not see `/usr/sbin/sshd` in the list, start it manually by running `/usr/sbin/sshd` in the notebook terminal.
5. Connect from your laptop terminal:
   ```bash
   ssh jovyan@jupyter-xhejtman---54est.dyn.cloud.e-infra.cz
   ```

### Building Your Own Custom Docker Image
* **Standard Custom Image:** Base your `Dockerfile` on `jupyter/minimal-notebook:hub-4.0.2` (see our [example Dockerfile](/examples/ceritsc/jupyterhub/Dockerfile-minimal))[span_97](start_span)[span_97](end_span). If building from another base image, install `jupyterlab` and copy [start-notebook.py](/examples/ceritsc/jupyterhub/start-notebook.py), [start-notebook.sh](/examples/ceritsc/jupyterhub/start-notebook.sh), [start-singleuser.py](/examples/ceritsc/jupyterhub/start-singleuser.py), [start-singleuser.sh](/examples/ceritsc/jupyterhub/start-singleuser.sh), and [start.sh](/examples/ceritsc/jupyterhub/start.sh) into `/usr/local/bin` with Unix (`LF`) line endings and executable permissions (`chmod a+rx /usr/local/bin/start*`).
* **Custom SSH-Enabled Image:** Base your image on `cerit.io/hubs/minimalnb:26-09-2024-ssh`, or install `openssh-server` in your custom image[span_99](start_span)[span_99](end_span):
  1. Add this configuration to `/etc/ssh/sshd_config.d/sshd.conf` (or `/etc/ssh/sshd_config`):
     ```ini title="sshd.conf"
     Port 2222
     AddressFamily any
     ListenAddress 0.0.0.0
     ListenAddress ::
     StrictModes no
     PubkeyAuthentication yes
     UsePAM yes
     X11Forwarding no
     PrintMotd no
     TCPKeepAlive yes
     PubkeyAcceptedKeyTypes +ssh-rsa
     ```
  2. **Security Requirement:** Delete all existing `/etc/ssh/ssh_host_*` files during the Docker build and regenerate them dynamically at container startup in `/usr/local/bin/start-notebook.sh`:
     ```bash title="start-notebook.sh"
     #!/bin/bash
     echo "WARNING: Use start-notebook.py instead"

     (export LD_LIBRARY_PATH=''; 
      rm -f /etc/ssh/ssh_host_*; 
      for i in rsa dsa ecdsa ed25519; do 
        ssh-keygen -q -f /etc/ssh/ssh_host_${i}_key -N '' -t $i; 
        ssh-keygen -f /etc/ssh/ssh_host_${i}_key.pub; 
      done)

     LD_LIBRARY_PATH='' /usr/sbin/sshd

     exec /usr/local/bin/start-notebook.py "$@"
     ```

### Automatic Idle Shutdown Policy
To ensure fair access to expensive cluster hardware (especially GPUs) for all researchers, an automated script evaluates active notebooks once every 24 hours (measuring peak 5-minute average utilization)[span_105](start_span)[span_105](end_span):

| Server Type | Idle Threshold | Grace Period Before Deletion |
| :--- | :--- | :--- |
| **Notebooks with GPU** | `< 0.005` GPU utilization (CPU usage is ignored) | **2 consecutive days** of inactivity|
| **CPU-Only Notebooks** | `< 0.1` CPU cores utilized | **4 consecutive days** of inactivity |

* **Email Warnings:** You will receive daily warning emails (sent to your preferred MetaCentrum email address) each day your notebook falls below the threshold, plus a final notification if the instance is deleted.
* **How to Keep Your Server Alive:** Simply running a calculation that exceeds the threshold resets your warning counter to zero automatically.

## Resource Utilization and Shutdown Mechanism

To promote effective computing, unused notebooks may be deleted based on resource usage. We have implemented a simple mechanism that decides if your notebook instance will be deleted. It performs evaluations once a day.

If **at least 1 GPU** was requested, the mechanism checks GPU usage and does not care about CPU usage (GPU is a *more expensive* resource). After 2 days of &lt;0.005 GPU usage, the notebook instance is deleted. The threshold `0.005` was chosen because this number is truly insignificant and means no usage. 

If **no GPU** was requested, the mechanism checks only CPU usage. After 4 days of &lt;0.1 CPU usage, the notebook instance is deleted. The threshold was chosen based on data collected by monitoring --- CPU usage below 0.1 suggests that the notebook just exists and no computation is performed.

The mechanism works for both ways as following: 

> Notebook's CPU usage is measured over 24h and is calculated as the average of notebook CPU usage (in CPU seconds) over 5-minute-long segments. The final maximum is chosen from all segments. If the resulting maximum *equals to zero/under 0.1*, the notebook instance is internally marked with "1" as the first warning. If usage is above 0.1, nothing happens.
>
> Notebook's GPU usage is measured over 24h and is calculated as the average portion of time graphics engine was active over 5-minute-long segments. The final maximum is chosen from all segments. If the resulting maximum *equals to zero/under 0.005*, the notebook instance is internally marked with "1" as the first warning. If usage is above 0.005, nothing happens.
> 
>  Next run performs the same but if maximum:
>  - is still less than 0.1 for CPU (0.005 for GPU), counter is increased by one. If counter reaches `threshold+1` (e.g. for CPU, 5 as 4 days have already passed), instance is deleted.
>  - changes from under the threshold above it, the mark is completely removed (you apparently started using notebook again).
>  - is over the threshold, nothing happens.


### Low Usage Notification

If the notebook is marked for deletion, you will receive an e-mail informing about the situation for every warning until instance is truly removed. You will get an e-mail informing about deletion as well. You are not forced to do anything about instance if you receive an email --- if the usage does not go up, it will be deleted. We recommend saving the results or copying them elsewhere if you receive a warning. The email is sent to the address configured in your MetaCentrum account as a preferred address.

## Exposing Local Applications  

Flare tunnel allows you to expose your local applications on the domain `flare.cloud.e-infra.cz`.  

Creating a tunnel:  

1. Install the Python package for tunnel management:  
```bash
pip install git+https://github.com/CERIT-SC/flare
```  
2. Start the application you want to expose.  
3. Create a tunnel:  
```bash
flare tunnel --port {port} --name {name}
```  
where `{port}` is the port on which your application is running, and `{name}` defines the URL where the application will be accessible.  
For example, the following command will expose an application running on port `8888` at the URL `https://myapp.flare.cloud.e-infra.cz`:  
```bash
flare tunnel --port 8888 --name myapp
```

### Creating Own SSH Enabled Image

You can easily base our minimal notebook image with the name: `cerit.io/hubs/minimalnb:26-09-2024-ssh`. Or you can create your own from scratch. Follow the guidelines above, how to create own notebook image and additionally install `openssh-server` package.

Put the following configuration into `/etc/ssh/sshd_config.d/sshd.conf` or if your base distribution does not use `/etc/ssh/sshd_config.d` then just to `/etc/ssh/sshd_config`:

```ini title="sshd.conf"
Port 2222
AddressFamily any
ListenAddress 0.0.0.0
ListenAddress ::
StrictModes no
PubkeyAuthentication yes
UsePAM yes
X11Forwarding no
PrintMotd no
TCPKeepAlive yes
PubkeyAcceptedKeyTypes +ssh-rsa
```

Also remove all `/etc/ssh/ssh_host_*` files in the image.

<Callout type="warning">
It is crucial to remove the `ssh_host_*` files from the image and create new files during image start. Otherwise the ssh connection is not secure!
</Callout>

The last step is to edit original `start-notebook.sh` file located in the image in `/usr/local/bin/start-notebook.sh` and add lines:

```bash
(export LD_LIBRARY_PATH=''; 
 rm -f /etc/ssh/ssh_host_*; 
 for i in rsa dsa ecdsa ed25519; do 
   ssh-keygen -q -f /etc/ssh/ssh_host_${i}_key -N '' -t $i; 
   ssh-keygen -f /etc/ssh/ssh_host_${i}_key.pub; 
 done)

LD_LIBRARY_PATH='' /usr/sbin/sshd
```

the whole file should look like this:
```bash title="start-notebook.sh"
#!/bin/bash
# Shim to emit warning and call start-notebook.py
echo "WARNING: Use start-notebook.py instead"

(export LD_LIBRARY_PATH=''; 
 rm -f /etc/ssh/ssh_host_*; 
 for i in rsa dsa ecdsa ed25519; do 
   ssh-keygen -q -f /etc/ssh/ssh_host_${i}_key -N '' -t $i; 
   ssh-keygen -f /etc/ssh/ssh_host_${i}_key.pub; 
 done)

LD_LIBRARY_PATH='' /usr/sbin/sshd

exec /usr/local/bin/start-notebook.py "$@"
```

## Run Job From Notebook

Jupyter Notebooks are great tool for interactive computing but sometimes your scripts can include a portion that is more resource-intensive. In this case, it is preferred to run this portion as a `Job` rather than inside the Notebook. Some of the reasons are:
1. You have to allocate a lot of resources for notebook even though most of the time, you don't need them. 
2. If the computation is too demanding, you might not be able to interact with the notebook environment because allocated reosurces are consumed by the computation &rarr; you can't interactively analyse the data from the notebook

### Sharing The Data From Notebook To Job
It is probable that you would like to reuse the data (or script) located in your Jupyter Notebook instance in the `Job`. As `Job` is a new object, you must attach the data to it. 

Your notebook can mount two different so-called `volumes` that are shareable:
1. Your notebook has a persistent volume mounted to `/home/jovyan` (or `/home/rstudio`) which is internally realized by an object called `PersistentVolumeClaim`. This object has a nice feature - it can be reused and mounted to any other Notebook or Job to any path.
2. If you chose to mount your metacentrum home (mounted to `/home/meta/[your_meta_username]`), another `PersistentVolumeClaim` object has been created for the home. This object can be reused and mounted to any other Notebook or Job to any path too.


To later use these two objects (`PersistentVolumeClaims` = PVCs) , you need to know their names:
1. Find out the name of PVC mounted to `/home/jovyan` (or `/home/rstudio`) by issuing command
```
kubectl get pvc | awk -v volume=$(df -h | awk '$1 ~ /^147\.251\.6\.218:/ {split($1, a, "/"); print a[length(a)]}') '$3 == volume {print $1}'
```
e.g.
```
rstudio@jupyter-testuser--pipemaster2:~$ kubectl get pvc | awk -v volume=$(df -h | awk '$1 ~ /^147\.251\.6\.218:/ {split($1, a, "/"); print a[length(a)]}') '$3 == volume {print $1}'
testuser-home-pipemaster <---- NAME OF THE PVC MOUNTED TO /home/rstudio
```

2. Find out the name of PVC mounted to `/home/meta/[your_username]` by issuing two commands:
  2.1 First, see what storage you mounted. If you didn't mount any meta storage, the output will be empty.
  ```
  df -h | awk '$NF ~ /^\/home\/meta/ {match($1, /@([^:]+):/, m); print m[1]}'
  ```
  e.g., 
  ```
  rstudio@jupyter-testuser--pipemaster2:~$ df -h | awk '$NF ~ /^\/home\/meta/ {match($1, /@([^:]+):/, m); 
  print m[1]}'
  storage-brno2.metacentrum.cz <---- MOUNTED META STORAGE
  ```
  2.2 Secondly, get the PVC name for metacentrum home by issuing command and matching its name with your chosen storage match with the storage name such as `brno2, brno12, plzen1, ...`
  ```
  kubectl get pvc | awk '$3 ~ /-data-sshfs$/ {print $1}'
  ```
  e.g.
  ```
  rstudio@jupyter-testuser--pipemaster2:~$kubectl get pvc | awk '$3 ~ /-data-sshfs$/ {print $1}'
  testuser-brno12-cerit-claim
  testuser-brno2-claim <----  THIS IS THE ONE because mounted meta home is storage-brno2.metacentrum.cz
  ```
  
Now you should know the names of the objects that we will use as volume mounts in the next Section on creating the Job itself.
  

### Creating The Job
In the `Job`, you will need to provide 4 things:
1. Image name to run
2. Script/Command to start
3. Resources
4. Volumes to Mount

#### Image
Job must start with some image. You should create a Docker image that will include all necesarry libraries  your script requires or software you want to run to process the data.

#### Script
Script can be built into the image or you can run script located in the mounted volumes (so from the PVCs we mentioned above).

If you interacted with the Notebook and you saved a script you would like to run as a Job in a path `/home/rstudio` (`/home/jovyan`) or in you meta home, you will be able to run this script in the Job, if the volume is mounted (more below)

#### Resources
You will need to specify what memory and CPU resources your Job needs.

#### Volumes to Mount
You can specify, if you want to mount any of the two PVCs from section above (so persistent home or metahome) to your Job. Generally, it makes sense to mount both (if you use Meta home) because you can directly share the data between Meta home, Notebook and Job. Moreover, the Job can write its outputs to either Meta home or Notebook's home dir which makes it easier for you to work with outputs (does not require any copying)



## Error Handling
You receive _HTTP 500:Internal Server Error_ when accessing the URL `/user/your_name`. Most likely, this error is caused by:
1. You chose MetaCentrum home you haven't used before -- The red 500 Error is followed by `Error in Authenticator.pre_spawn_start`
2. You chose MetaCentrum home you don't have access to -- The red 500 Error is followed by `Error in Authenticator.pre_spawn_start`
3. While spawning, `Error: ImagePullBackOff` appears

Solutions:
1. Log out and log in back
2. You can not access the home even after logging out and back in -- you are not permitted to use this particular home
3. Clicking on small arrow `Event log` provides more information. Most certainly, a message tagged `[Warning]` is somewhere among all of them and it provides more description. It is highly possible the repo and/or image name is misspelled. 
   - please wait for 10 minutes
   - The service has a timeout of 10 minutes and during this time, it is trying to create all necessary resources. Due to error, creation won't succeed and after 10 minutes you will see red progress bars with message `Spawn failed: pod/jupyter-[username] did not start in 600 seconds!`. At this point, it is sufficient to reload the page and click on `Relaunch server`.
