Tento krátký tutoriál ukazuje, jak nasadit vlastní webový server v Kubernetes pomocí `kubectl`. Použijeme již existující příklad [hello-kubernetes](https://github.com/paulbouwer/hello-kubernetes), ale s trochu podrobnějším vysvětlením. Tutoriál zdaleka nepokrývá vše, co lze v Kubernetes nastavit a udělat, ale poskytne vám první zkušenost.

Nasadíme jednoduchou webovou aplikaci, která běží z Docker image a zobrazuje „Hello world“ spolu se jménem `Podu` a informacemi o `OS uzlu`.

*DŮLEŽITÉ*
Pokud se předem nedohodnete jinak, můžete pro osobní projekty a experimenty používat `kuba-cluster`. Zde musíte pracovat ve svém namespace, jehož název je odvozen od vašeho příjmení s příponou `-ns`. Jména ale nejsou jedinečná, proto doporučujeme svůj namespace ověřit v `Rancheru` v rozbalovací nabídce v levém horním rohu `kuba-cluster` a `Project/Namespaces`.

## Vytvoření souborů

K nasazení aplikace musíme vytvořit alespoň 3 Kubernetes zdroje (resources) -- `Deployment`, `Service`, `Ingress`.

### 1. Deployment
Vytvořte nový adresář, např. `hello-world`, a v něm nový soubor `deployment.yaml` s tímto obsahem:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-kubernetes
spec:
  replicas: 3
  selector:
    matchLabels:
      app: hello-kubernetes
  template:
    metadata:
      labels:
        app: hello-kubernetes
    spec:
      securityContext:
        runAsUser: 1000
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: hello-kubernetes
        image: paulbouwer/hello-kubernetes:1.9
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop:
            - ALL
        env:
          - name: KUBERNETES_NAMESPACE
            valueFrom:
              fieldRef:
                fieldPath: metadata.namespace
          - name: KUBERNETES_POD_NAME
            valueFrom:
              fieldRef:
                fieldPath: metadata.name
          - name: KUBERNETES_NODE_NAME
            valueFrom:
              fieldRef:
                fieldPath: spec.nodeName
        ports:
        - containerPort: 8080
```
Tento příklad se skládá z těchto polí:
- `.metadata`
  - `.name` určuje název deploymentu
- `.spec`
  - `.replicas` určuje počet replikovaných Podů, které budou vytvořeny
  - `.selector` definuje, jak `Deployment` najde `Pody`, které má spravovat. Zde je vybrán štítek (label) definovaný v šabloně `Podu` (`app: hello-kubernetes`). Je možné použít sofistikovanější pravidla výběru, pokud se hodnoty `app: hello-kubernetes` shodují v sekcích `spec:` a `template:` šablony `Podu`.
  - `.template`
    - `.metadata.labels` zde se `Pody` označují štítky
    - `.spec` specifikace šablony `Podu`
      -  `.containers` pole definující kontejnery, které poběží. Každá položka musí obsahovat `name, image`
      -  `.containers.securityContext` definuje, pod jakým uživatelem a případně skupinou bude kontejner běžet. *DŮLEŽITÉ* z bezpečnostních důvodů musí kontejnery běžet pod uživatelem a skupinou, které nejsou root. Více v části o *PodSecurityPolicy* níže
      -  `.containers.env` nastavuje proměnné prostředí kontejneru. Mohou být převzaty z jiných polí objektu nebo z jiných typů objektů (např. Secret)

Kompletní referenční dokumentace zdrojů a jejich povolených polí a podpolí je dostupná [online](https://kubernetes.io/docs/reference/generated/kubernetes-api/v1.30/). Nezapomeňte na správné odsazení!

### 2. Service
Za druhé musíme vytvořit `Service`, což je abstraktní způsob zpřístupnění aplikace jako síťové služby.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hello-kubernetes-svc
spec:
  type: ClusterIP
  ports:
  - name: hello-kubernetes-port
    port: 80
    targetPort: 8080
  selector:
    app: hello-kubernetes
```
Tento soubor vytvoří nový objekt `Service` s názvem „hello-kubernetes-svc“, který cílí na TCP port 8080 na libovolném `Podu` s označením `app=hello-kubernetes`.

Service může mapovat libovolný příchozí port na targetPort. Ve výchozím nastavení je targetPort nastaven na stejnou hodnotu jako pole containerPort. Výchozí protokol je TCP, ale lze použít i jiné podporované protokoly (UDP, HTTP, SCTP, PROXY).

### 3. Ingress

Nakonec musíme vytvořit `Ingress`, který zpřístupňuje HTTP a HTTPS cesty z vnějšího světa do světa clusteru. Provoz je řízen pravidly definovanými v tomto zdroji.
Své deploymenty můžete zpřístupnit [několika způsoby](../kubernetes/expose) podle protokolu — pro webový provoz viz [Zpřístupnění HTTP aplikací](../kubernetes/expose/expose-http) a pro ostatní protokoly [Zpřístupnění non-HTTP aplikací](../kubernetes/expose/expose-network).
Můžete použít libovolný název, ale musí splňovat 2 požadavky:
- název se skládá pouze z písmen, číslic a znaku '-'
- název končí na `.dyn.cloud.e-infra.cz`

Název se vyplňuje do `spec.rules.host` a do `spec.tls`. Než nějaký název použijete, zkontrolujte v prohlížeči, že už neexistuje. Po vytvoření trvá asi minutu, než vznikne nový DNS záznam, takže aplikace nebude na zadaném názvu dostupná hned, počkejte minutu.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: hello-kubernetes-ingress
  annotations:
    kubernetes.io/tls-acme: "true"
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - "test-hello.dyn.cloud.e-infra.cz"
      secretName: test-hello-dyn-cloud-e-infra-cz-tls
  rules:
  - host: "test-hello.dyn.cloud.e-infra.cz"
    http:
      paths:
      - backend:
          service:
            name: hello-kubernetes-svc
            port:
              number: 80
        path: /
        pathType: ImplementationSpecific
```

Tento příklad se skládá z těchto polí:
- `.metadata`
  - `.name` určuje název
  - `.annotations` ingress často používá anotace ke konfiguraci voleb v závislosti na ingress kontroleru. Používáme kontroler `nginx` a možné anotace jsou uvedeny [zde](https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/annotations/). Zde použité anotace jsou nezbytné pro správnou funkčnost a automaticky vytvářejí TLS certifikát, takže se o HTTPS nemusíte starat – je zajištěno automaticky
 - `.spec` obsahuje všechny informace potřebné ke konfiguraci load balanceru, především však pravidla, která se porovnávají se všemi příchozími požadavky
  - `.tls` zajišťuje zabezpečení `Ingressu`
    - `hosts` musí přesně odpovídat DNS názvu, který bude použit
    - `secretName` musí odpovídat DNS názvu, ale *všechny tečky se nahradí znakem '-' a na konec se přidá -tls*
  - `.rules` je nejdůležitější část
    - `host` je volitelný, pokud je uveden, pravidla se vztahují na tento host
    - `paths` (například `/testpath`), z nichž každá má přiřazený backend definovaný pomocí `service.name` a `service.port.name` nebo `service.port.number`. `service.port.number` je port, který služba zpřístupňuje, tedy ve službě uvedený jako `spec.ports.port`; obdobně `service.ports.[i].name` odpovídá `spec.ports.[i].name`. Lze určit i typ cesty, více o tom [zde](https://kubernetes.io/docs/concepts/services-networking/ingress/#path-types)

### 4. Vytvoření
Nyní vytvořte všechny zdroje tak, že jako argument použijete celý adresář, a zadejte svůj namespace:
```bash
kubectl apply -f hello-world -n [namespace]
deployment.apps/hello-kubernetes created
ingress.networking.k8s.io/hello-kubernetes-ingress created
service/hello-kubernetes-svc created
```

Stav nasazených zdrojů můžete zkontrolovat pomocí `kubectl get [pods | services | ingress] -n [namespace]` a jakmile všechny běží, můžete otevřít URL a zobrazí se vám ukázková stránka.

## Další přizpůsobení
V souboru každého zdroje můžete nastavit různá pole, z nichž mnohá zde nebyla použita. Jednou z nejžádanějších funkcí je předávání proměnných prostředí do `Deploymentů`, pokud je vytvářené kontejnery potřebují. Použijeme jednu proměnnou prostředí ke změně zobrazované zprávy. Na konec přidejte novou sekci `env`, která hodnotu předá do podu. Poté znovu spusťte `kubectl apply -f hello-world -n [namespace]`, aby se změny aplikovaly. Když nyní web otevřete, zobrazí se nová zpráva!

## Vytvoření PersistentVolumeClaim
Pokud potřebujete trvalé úložiště, můžete vytvořit NFS volume a připojit ho v `Deploymentu`.

Příklad: vytvořte soubor `pvc.yaml` a nastavte `[pvc-name]` na požadovaný název a `[capacity]` na požadovanou kapacitu.
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: [pvc-name]
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: [capacity]Gi
  storageClassName: nfs-csi
```
Poté spusťte `kubectl apply -f pvc.yaml -n [namespace]`, kde `[namespace]` je namespace, ve kterém chcete mít PVC vytvořené. Zda vše proběhlo správně, ověříte příkazem
```bash
kubectl get pvc -n [namespace]
NAME                                                               STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
[pvc-name]                                                    Bound    pvc-bcdcea2e-3019-409b-8b0f-18eb50d72c21   1Gi        RWX            csi-nfs        11d
```

Claim se do `Deploymentu` (nebo jiných objektů, jako `Job, StatefulSet, DaemonSet` apod.) připojuje ve 2 krocích:
- vytvořte pole `volumes` pod `spec.template`
- vytvořte pole `volumeMounts` pod `spec.template.spec.containers[kontejner_ve_kterém_bude_pvc_připojeno]`

`volumes` představuje seznam svazků k připojení s alespoň:
- polem `name`
- typem zdroje, který bude připojen (zde `persistentVolumeClaim`), spolu s názvem zdroje (tím, který je uveden v `metadata.name` PVC)

`volumeMounts` připojuje položky z `volumes` do určité cesty uvnitř kontejneru. V kontejneru vše, co se uloží do cesty `/work`, zůstane zachováno a může být sdíleno mezi více kontejnery (jeden svazek lze připojit vícekrát, pokud je jeho typ `ReadWriteMany`, což NFS je)

```yaml
spec:
  replicas: ...
  selector:
    matchLabels:
      ...
  template:
    metadata:
      labels:
        ...
    spec:
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: flask-web
          image: alpine:3.8
          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop:
              - ALL
          ports:
            - containerPort: 8888
          volumeMounts:            <---------------- SEZNAM VOLUME MOUNTS
            - mountPath: /work
              name: shared-volume
      volumes:        <---------------- SEZNAM VOLUMES
      - name: shared-volume
        persistentVolumeClaim:
          claimName: my-first-claim
```

## Pod Security Policy
Z bezpečnostních důvodů není v `kuba-cluster` povoleno vše.

Seznam (ne)povolených akcí:
- Allow Privilege Escalation:  false
- Fs Group: musí běžet jako 1-65535
- User: musí běžet jako non-root
- Supplemental groups: musí běžet jako 1-65535
- Volumes: lze připojit `configMap, emptyDir, projected, secret, downwardAPI, persistentVolumeClaim`

Každý deployment, který se pokusí běžet jako root, nebude vytvořen a zůstane ve stavu podobném tomuto:
```bash
NAME               READY   UP-TO-DATE   AVAILABLE   AGE
hello-kubernetes   0/1     1            0           7m8s
```
 (všimněte si READY 0/3 a AVAILABLE 0; více by prozradily logy a příkaz describe)
