## AI for Science. Built for Researchers. Run securely in e-INFRA CZ.

CERIT‑SC, a core component of the national research infrastructure **e‑INFRA CZ**, operates a sovereign, **on‑premise AI-as-a-Service (AIaaS) platform** designed specifically for the scientific and academic community. Powered by cutting‑edge **NVIDIA DGX‑H100, B200, and B300‑class** systems, the platform delivers petaflop‑scale computational performance for high‑throughput, low‑latency inference.

The environment hosts state‑of‑the‑art open‑weights Large Language Models (LLMs), multimodal vision‑language architectures, and embedding models. Beyond raw model inference, CERIT‑SC provides a comprehensive **scientific AI ecosystem**—spanning conversational [Open WebUI interface](../ai-as-a-service/chat-ai), programmatic [OpenAI‑compatible APIs](../ai-as-a-service/ai-api), interactive JupyterHub coding assistants, IDE integrations, Model Context Protocol (MCP) tool servers, and automated agentic workflows.

### Data Sovereignty, Privacy & Scientific Compliance

Scientific research frequently involves unpublished manuscripts, proprietary source code, patentable intellectual property, and sensitive datasets. Unlike commercial cloud providers, the CERIT‑SC AI platform guarantees complete institutional data sovereignty:

* **Strict On‑Premise Isolation:** All inference engines run exclusively on dedicated hardware within the e‑INFRA CZ infrastructure. Prompts, context attachments, and generated completions never leave the local environment (with the sole exception of explicit, user‑triggered external web search queries).
* **Zero Data Mining or Model Training:** User interactions are never used to train, fine‑tune, or align global models. All system administrators operate under strict Non‑Disclosure Agreements (NDAs).
* **Privacy‑First API Architecture:** For research workflows involving sensitive or protected datasets, querying models directly via the [OpenAI‑compatible API](../ai-as-a-service/ai-api) completely bypasses the WebUI conversational database layer, routing requests directly to the stateless inference engines.
* **Isolated Environments for Regulated Data:** If your research involves highly sensitive data or strict regulatory compliance (e.g., clinical/health data under GDPR), contact us at `k8s@cerit-sc.cz` to discuss a dedicated, isolated deployment.

For complete technical details on logging, retention, and storage, see the [AI Data Privacy Policy](../ai-as-a-service/ai-data-privacy).

## Best Practices & Fair Use Policy

Because the e‑INFRA CZ AI platform is a shared, finite computational resource, unoptimized automated workloads directly impact queue times for other researchers. Please adhere to the following operational guidelines to ensure low latency and fair access across the scientific community:

* **Distinguish Interactive vs. Automated Load:** Interactive sessions via **Open WebUI** or **JupyterHub** generate negligible load compared to automated API scripts; researchers do not need to worry about resource limits during standard interactive work. However, when executing high‑volume batch jobs or automated evaluation pipelines via the **API**, please be mindful that excessive token consumption increases queue times for the entire community.
* **Match Model Scale to Task Complexity:** Avoid routing simple classification, formatting, or extraction tasks to massive, reasoning‑heavy models (such as **Kimi** or **GLM**). Large reasoning models incur significantly higher latency without yielding quality improvements on basic prompts. In multi‑step or agentic architectures, use a frontier orchestrator model (`agentic` / `thinker`) to plan and delegate routine sub‑tasks to faster, lightweight models (`mini`).
* **Constrain Parallel Agent Concurrency:** Do not spawn large numbers of simultaneous API threads or concurrent agents. Platform concurrency is actively governed by upper rate limits to protect cluster stability and prevent GPU memory exhaustion.
* **Configure Models by Functional Role—Do Not Chase Live Metrics:** Avoid dynamically switching target models in your scripts based on utilization figures on the status page. Telemetry metrics are slightly delayed, and automated load‑chasing triggers severe traffic oscillations across GPU nodes. Bind your workflows to appropriate functional roles or model aliases and submit tasks normally; standard queue wait times are minimal.
* **Schedule Compute‑Intensive Batch Jobs for Off‑Peak Hours:** If your research requires large‑scale dataset annotation, bulk embedding generation, or extensive benchmark runs via the API, schedule these batch workloads during nights or weekends when interactive platform traffic is lowest.
