title: Limitations of Running Docker Images
---


## No Root

While it is not a common feature, in our container platform, users cannot run Docker images with escalated privileges, that is, as the `root` user or using elevated `capability`. Privilege escalation is not possible even when running the Docker image, so `sudo` or `su` commands cannot be used. It is also not possible to use more than one user in the container; there is no mechanism to switch between two users.

To meet this requirement, either the Docker image must specify the user that the image runs as, or specify `runAsUser: UID` in the corresponding YAML file. For example, `USER 1000` in the Dockerfile. Specifying `UID` (and not a name) is a hard requirement. If you try to run an image that does not have a numeric `UID`, you receive the following error, replacing `taskmaster` with the actually used name:
```
Error: container has runAsNonRoot and image has non-numeric user (taskmaster), cannot verify user is non-root 
```

If `USER` in the Dockerfile or `runAsUser` in YAML is not specified, you receive the following error:
```
Error: container has runAsNonRoot and image will run as root
```
To fix this, you need to specify either `USER`, for example, `USER 1000`, or `runAsUser`, for example, `runAsUser: 1000`, in YAML.

On the other hand, you have full root capability during Docker image building.

### Consequences

* You cannot install any package into a running container unless you prepare the container in advance:

  1. Install the `fakeroot` package
  2. Run `chown -R uid /etc /lib* /usr /var /bin` during the Docker build process. Replace `uid` with the real user ID, for example, 1000.

  However, this is an anti-pattern of using Docker images; you should avoid this approach mainly because if the running container is restarted (which can happen sometimes), all installed packages and other modifications are lost.

* You cannot bind ports below 1024. This means that services need to listen on higher ports, for example, 8080, and so on. This does not mean you cannot create a service that listens on port 443 or 80 for the outside world. Just follow [Exposing applications](../kubernetes/expose). This issue is mostly related to web servers (like NGINX and Apache; for NGINX, there is a prepared non-privileged container: `nginxinc/nginx-unprivileged:latest`), SSH server, and Samba server. All these servers can be reconfigured to listen on higher ports.

* You cannot write to directories such as `/run` or `/var/log/`. In this case, you do not need to rebuild the image and change rights. There is a workaround: mount an `emptyDir` volume into those directories. Just merge the following two fragments in the deployment YAML:

```yaml
volumes:
- name: log
  emptyDir: {}

volumeMounts:
- name: log
  mountPath: /var/log
```
If there are `volumes` and `volumeMounts` sections already, just add these items without the `volumes` and `volumeMounts` lines.
