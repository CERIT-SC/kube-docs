[MinIO Operator](https://min.io/docs/minio/kubernetes/upstream/index.html) je nasazen jako cluster-wide služba Kubernetes. Umožňuje uživatelům vytvářet a spravovat tenanty objektového úložiště MinIO S3 napříč celým clusterem.

MinIO Operator obsahuje vlastní zdroj s názvem `Tenant`, který zajišťuje vytvoření a správu instancí objektového úložiště. Kompletní dokumentaci ke struktuře najdete [zde](https://min.io/docs/minio/kubernetes/upstream/index.html). Oficiální návod na vytvoření MinIO Tenanta je dostupný [zde](https://github.com/minio/operator/blob/master/docs/examples.md).

Pro usnadnění poskytujeme několik funkčních příkladů rozdělených do sekcí, viz níže.

Celkové schéma komponent MinIO je zobrazeno níže:
![minio-schema](/img/ceritsc/minio-schema.svg)

## Nasazení Single instance

Můžete začít s ukázkovou instancí, která je ideální pro testovací účely. Tento příklad vytvoří zdroj `Tenant`, který je spravován nainstalovaným MinIO Operátorem. Příklad si můžete stáhnout [zde](/examples/ceritsc/manifests/minio-minimal-tenant.yaml).

```yaml
apiVersion: minio.min.io/v2
kind: Tenant
metadata:
  name: myminio
spec:
  ## Name of the tenant instance
  name: myminio
  ## Create users in the Tenant using this field. Make sure to create secrets per user added here.
  ## Secret should follow the format used in `minio-creds-secret`.
  users:
    - name: myminio-user-secret
  ## Pre create buckets
  buckets:
    - name: mybucket
  certificate:
    requestAutoCert: true ## if true, Minio uses HTTPS protocol - important for Ingress, if false, HTTP (no encryption) is used
  ## Specification for MinIO Pool(s) in this Tenant.
  pools:
    ## Servers specifies the number of MinIO Tenant Pods / Servers in this pool.
    ## For standalone mode, supply 1. For distributed mode, supply 4 or more.
    ## Note that the operator does not support upgrading from standalone to distributed mode.
    - servers: 1
      ## custom pool name
      name: pool-0
      ## volumesPerServer specifies the number of volumes attached per MinIO Tenant Pod / Server.
      volumesPerServer: 1
      ## select NFS storage class
      storageClassName: nfs-csi
      ## This VolumeClaimTemplate is used across all the volumes provisioned for MinIO Tenant in this Pool.
      volumeClaimTemplate:
        metadata:
          name: data
        spec:
          accessModes:
            - ReadWriteOnce
          resources:
            requests:
              storage: 2Gi
      ## Configure Pod's security context
      securityContext:
        runAsNonRoot: true
        fsGroup: 1000
        runAsUser: 1000
        runAsGroup: 1000
      ## Configure container security context
      containerSecurityContext:
        runAsNonRoot: true
        privileged: false
        runAsUser: 1000
        runAsGroup: 1000
        allowPrivilegeEscalation: false
        capabilities:
          drop:
          - ALL
        seccompProfile:
          type: "RuntimeDefault"
```

Tento příklad rovněž vyžaduje nasazení secret pro uživatele. Příklad lze stáhnout [zde](/examples/ceritsc/manifests/minio-minimal-tenant-secret.yaml).

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: myminio-user-secret
type: Opaque
data:
  CONSOLE_ACCESS_KEY: Y29uc29sZQ== # "console", base64 encoding
  CONSOLE_SECRET_KEY: Y29uc29sZTEyMw== # "console123", base64 encoding
```

Pro nastavení vlastního `access_key` (uživatelské jméno) a `secret_key` (heslo) můžete hodnoty ručně zakódovat nebo dekódovat pomocí následujících příkazů:

```bash
# encode
echo -n "securepassword" | base64
# decode
echo -n "c2VjdXJlcGFzc3dvcmQ=" | base64 -d
```

Následně secret a MinIO Tenant nasadíte pomocí:

```bash
kubectl create -n [namespace] -f example-tenant-secret.yaml -f example-tenant.yaml
````

Pokud je nasazení úspěšné, měli byste vidět pod s názvem myminio-pool-0-0 (nebo podobným, v závislosti na vaší konfiguraci), který běží ve zvoleném namespace.

## Přístup k MinIO

Pro přístup k MinIO z jiných podů použijte služby `myminio-console` a `myminio-hl`, které jsou automaticky vytvořeny. Tyto služby fungují jako DNS názvy, což umožňuje ostatním aplikacím v rámci Kubernetes clusteru používat je jako koncové body (endpoints).

Při přístupu z jiného namespace použijte plně kvalifikovaný doménový název (FQDN), např. `myminio-hl.[namespace].svc.cluster.local`.

- `myminio-console:9443` — Poskytuje webové rozhraní pro správu MinIO.
- `myminio-hl:9000` nebo `minio:<PORT>` — Poskytuje S3-kompatibilní API endpoint pro přístup k objektovému úložišti. Hodnota `<PORT>` je buď `443` (pokud je `requestAutoCert=true`) nebo `80` (pokud je requestAutoCert=false).


### Certifikáty


Pokud je requestAutoCert=true, automaticky se generují samopodepsané certifikáty. V důsledku toho mohou aplikace hlásit neznámou certifikační autoritu (CA). Tento problém lze vyřešit buď poskytnutím správného CA certifikátu aplikaci, nebo konfigurací vlastního Issuera pro použití externích certifikátů pro MinIO. Pokud je použit výchozí AutoCert, odpovídající CA certifikát je dostupný v každém  namespace v ConfigMap s názvem kube-root-ca.crt, pod klíčem ca.crt.


### Zpřístupnění MinIO mimo Kubernetes pomocí Ingress

Pro zpřístupnění MinIO mimo cluster doporučujeme použít Helm chart `Tenant` a nakonfigurovat sekci `ingress` v Tenant resource.

#### Krok 1: Přidejte MinIO Helm repozitář

Nejprve přidejte MinIO Operator Helm repository a aktualizujte local Helm cache:

```bash
helm repo add minio-operator https://operator.min.io
helm repo update
```

#### Krok 2: Vygenerujte výchozí hodnoty

Vytvořte výchozí soubor `values.yaml`: 

```bash
helm show values minio-operator/tenant > values.yaml
```

#### Krok 3: Nakonfigurujte Ingress v souboru `values.yaml`

Upravte soubor `values.yaml` a nastavte sekci ingress následovně:

```yaml
ingress:
  api:
    enabled: true
    ingressClassName: "nginx"
    labels: { }
    annotations:
      cert-manager.io/cluster-issuer: letsencrypt-prod
      kubernetes.io/tls-acme: "true"
      nginx.ingress.kubernetes.io/backend-protocol: HTTPS
      nginx.ingress.kubernetes.io/custom-http-errors: "599"
    tls:
    - hosts:
      - myminio-my-namespace.dyn.cloud.e-infra.cz
      secretName: my-secret-cloud-e-infra-cz
    host: myminio-my-namespace.dyn.cloud.e-infra.cz
    path: /
    pathType: Prefix
  console:
    enabled: true
    ingressClassName: "nginx"
    labels: { }
    annotations:
      cert-manager.io/cluster-issuer: letsencrypt-prod
      kubernetes.io/tls-acme: "true"
      nginx.ingress.kubernetes.io/backend-protocol: HTTPS
      nginx.ingress.kubernetes.io/custom-http-errors: "599"
    tls:
    - hosts:
      - myminio-ui-my-namespace.dyn.cloud.e-infra.cz
      secretName: my-secret-ui-cloud-e-infra-cz
    host: myminio-ui-my-namespace.dyn.cloud.e-infra.cz
    path: /
    pathType: Prefix
```

#### Krok 4: Instalace Tenant

Nainstalujte MinIO Tenanta pomocí upraveného souboru `values.yaml`

```bash
helm install myminio -n [mynamespace]  minio-operator/tenant -f values.yaml
```
#### Krok 5: Přístup k MinIO

- MinIO Console: `https://myminio-ui-my-namespace.dyn.cloud.e-infra.cz`
- S3 API Endpoint: `https://myminio-my-namespace.dyn.cloud.e-infra.cz`

#### ✅ Důležité:

- **Oddělené TLS Secrety:** Nepoužívejte stejný `secretName` pro API i konzoli. Každý Ingress musí mít svůj unikátní TLS secret.
- **Backend protokol:** Pokud je nastavena hodnota `requestAutoCert=true` ujistěte se, že je nastavena anotace: `nginx.ingress.kubernetes.io/backend-protocol: HTTPS`.
- **Chybové hlášky MinIO:** Nastavte `nginx.ingress.kubernetes.io/custom-http-errors: "599"` aby se zabránilo vlastnímu zpracování chyb ze strany NGINX, které by mohlo skrýt vlastní chybové zprávy MinIO.

## Nasazení MinIO s podporou proxy

Při nasazování Tenanta v Kubernetes clusteru, který vyžaduje HTTP(S) proxy, je nutné nastavit proxy konfiguraci pomocí proměnných prostředí.

### Krok 1: Nastavte proxy proměnné

- `HTTPS_PROXY`: `http://proxy.ics.muni.cz:3128`
- `HTTP_PROXY`: `http://proxy.ics.muni.cz:3128`
- `NO_PROXY`: `.svc.cluster.local,.svc,10.0.0.0/8,147.251.0.0/16,2001:718:801::/48,127.0.0.1,::1,.cloud.trusted.e-infra.cz`

Proměnná `NO_PROXY`je zásadní pro zajištění toho, aby MinIO nesměroval provoz přes proxy pro místní síťové komunikace v rámci clusteru. To je obzvlášť důležité pro komunikaci v rámci `kubas-cluster`.

### Krok 2: Nakonfigurujte soubor `values.yaml`

Přidejte následující konfiguraci pod sekci `tenant.env`:

```yaml
tenant:
 env:
 - name: HTTPS_PROXY
   value: http://proxy.ics.muni.cz:3128
 - name: HTTP_PROXY
   value: http://proxy.ics.muni.cz:3128
 - name: NO_PROXY
   value: ".svc.cluster.local,.svc,10.0.0.0/8,147.251.0.0/16,2001:718:801::/48,127.0.01,::1,.cloud.trusted.e-infra.cz"
```

### ✅ Poznámky:

- Ujistěte se, že hodnota `NO_PROXY` zahrnuje všechny local networks a internal services, aby se předešlo zbytečnému použití proxy.
- Důkladně zkontrolujte nastavení `NO_PROXY`, zejména pro rozsahy IPv6, protože nesprávná konfigurace může způsobit problémy s konektivitou v rámci clusteru.

## Network Policy

Pro zvýšení zabezpečení lze použít **NetworkPolicy** k omezení přístupu k úložišti MinIO S3, a povolit tak připojení pouze z konkrétních podů. Více informací naleznete v [dokumentaci k síťovým politikám.](../kubernetes/security)

Ve výchozím nastavení je externí přístup (např. z veřejného internetu) zakázán. Pokud je to však potřeba, je možné MinIO zpřístupnit pomocí [Load Balancer](../kubernetes/expose#other-applications) nebo Ingressu (viz výše).

### Příklad 1: NetworkPolicy pro MinIO Tenant

Následující příklad omezuje příchozí (ingress) a odchozí (egress) síťový provoz pro MinIO `Tenant`. To umožňuje:

- Odchozí komunikaci k místnímu DNS resolveru.
- Odchozí komunikaci k MinIO Operátoru nainstalovanému v rámci Kubernetes clusteru.
- Příchozí komunikaci z jakéhokoli podu na porty MinIO S3 API (`9000`) a webové konzole (`9443`).

Tento příklad si můžete stáhnout [zde](/examples/ceritsc/manifests/minio-minimal-tenant-np.yaml).

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: myminio-np
spec:
  podSelector:
    matchLabels:
      # This NetworkPolicy is applied to the `myminio` Tenant
      app: myminio
  policyTypes:
  - Egress
  - Ingress
  egress:
    # Enables egress communication to the local DNS resolver
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    # Enables egress communication to the Minio operator installed in Kubernetes.
  - to:
    - ipBlock:
        cidr: 10.43.0.1/32
    - ipBlock:
        cidr: 10.16.62.14/32
    - ipBlock:
        cidr: 10.16.62.15/32
    - ipBlock:
        cidr: 10.16.62.16/32
    - ipBlock:
        cidr: 10.16.62.17/32
    - ipBlock:
        cidr: 10.16.62.18/32
    ports:
    - port: 6443
      protocol: TCP
  ingress:
    # Enables ingress communication from any Pod to the 9000 and 9443 ports
    # for web management console access and S3 connection
  - from:
    - podSelector: {}
    ports:
    - protocol: TCP
      port: 9000
    - protocol: TCP
      port: 9443
```

### Příklad 2: Síťová politika pro aplikaci přistupující k MinIO

Následující politika umožňuje konkrétní aplikaci (myapplication) přístup k MinIO S3 API na portu `9000`.

Tento příklad si můžete stáhnout [zde](/examples/ceritsc/manifests/minio-minimal-application-np.yaml).

```yaml
kind: NetworkPolicy
apiVersion: networking.k8s.io/v1
metadata:
  name: myapplication-allow-s3
spec:
  podSelector:
    matchLabels:
      # This NetworkPolicy is applied to `myapplication` Pod
      app: myapplication
  policyTypes:
  - Egress
  egress:
    # Enables egress S3 communication from `myapplication` to the `myminio` Tenant
  - to:
    - podSelector:
        matchLabels:
          app : myminio
    ports:
    - protocol: TCP
      port: 9000
```

### ✅ Shrnutí:

- **MinIO NetworkPolicy:** zabezpečuje instance MinIO řízením jak příchozího (ingress), tak odchozího (egress) síťového provozu.
- **Aplikační NetworkPolicy:** umožňuje interakci s MinIO S3 API pouze vybraným aplikacím.

## OIDC autentizace pro MinIO pomocí e-INFRA CZ SSO

MinIO lze nakonfigurovat tak, aby využívalo **e-INFRA CZ Single Sign-On (SSO)** prostřednictvím **OIDC (OpenID Connect)**. Tento návod předpokládá, že vaše služba MinIO byla zaregistrována v [e-INFRA CZ SP Admin Portal](https://spadmin.e-infra.cz/) a že jste získali  **Client ID** a **Client Secret**.

---

### Krok 1: Zaregistrujte MinIO v SP Admin

Během procesu registrace na [spadmin.e-infra.cz](https://spadmin.e-infra.cz/), nakonfigurujte následující:

- **Callback URL:** `https://<your-console-url>/oauth_callback`
- **Scopes:** `eduperson_entitlement, profile, email`
- **Authorization flow:** `authorization code`
- **Token endpoint authentication method:** `client_secret_basic`
- **PKCE Code Challenge Method:** `SHA256 code challenge`
- **Enable introspection endpoint access**

### Krok 2: Nakonfigurujte proměnné prostředí MinIO

Na straně MinIO nastavte následující proměnné prostředí:

```yaml
MINIO_IDENTITY_OPENID_CONFIG_URL: https://login.e-infra.cz/oidc/.well-known/openid-configuration
MINIO_IDENTITY_OPENID_CLIENT_ID: <client id>
MINIO_IDENTITY_OPENID_CLIENT_SECRET: <client secret>
MINIO_IDENTITY_OPENID_SCOPES: eduperson_entitlement,profile,email
MINIO_IDENTITY_OPENID_CLAIM_NAME: eduperson_entitlement
MINIO_IDENTITY_OPENID_REDIRECT_URI: https://<console url>/oauth_callback
MINIO_IDENTITY_OPENID_DISPLAY_NAME: "e-INFRA CZ"
MINIO_IDENTITY_OPENID_CLAIM_USERINFO: on
```

### Krok 3: Bezpečné uložení Secretů

**Není doporučeno** ukládat citlivá data, jako je `MINIO_IDENTITY_OPENID_CLIENT_SECRET`, přímo do souboru `values.yaml`. Místo toho vytvořte **Kubernetes Secret**:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: <secret-name>
type: Opaque
stringData:
  config.env: |-
    export MINIO_ROOT_USER="<admin-username>"
    export MINIO_ROOT_PASSWORD="<admin-password>"
    export MINIO_IDENTITY_OPENID_CONFIG_URL: https://login.e-infra.cz/oidc/.well-known/openid-configuration
    export MINIO_IDENTITY_OPENID_CLIENT_ID: <client-id>
    export MINIO_IDENTITY_OPENID_CLIENT_SECRET: <client-secret>
    export MINIO_IDENTITY_OPENID_SCOPES: eduperson_entitlement,profile,email
    export MINIO_IDENTITY_OPENID_CLAIM_NAME: eduperson_entitlement
    export MINIO_IDENTITY_OPENID_REDIRECT_URI: https://<console url>/oauth_callback
    export MINIO_IDENTITY_OPENID_DISPLAY_NAME: "e-INFRA CZ"
    export MINIO_IDENTITY_OPENID_CLAIM_USERINFO: on
    export HTTPS_PROXY=http://proxy.ics.muni.cz:3128
    export NO_PROXY=".svc.cluster.local,.svc,10.0.0.0/8,147.251.0.0/16,2001:718:801::/48,127.0.01,::1,.cloud.trusted.e-infra.cz"
```

Nahraďte:

- `<admin-username>` svým uživatelským jménem správce MinIO.
- `<admin-password>` svým heslem správce MinIO.
- `<client-id>` a `<client-secret>` hodnotami získanými při registraci v SP Admin.
- `<your-console-url>` adresou URL vaší MinIO konzole.
- `<secret-name>` s vlastním názvem pro Secret.



### Krok 4: Odkazy na Secret v souboru values.yaml

Ve svém souboru values.yaml odkažte na vytvořený Secret následujícím způsobem:

```yaml
tenant:
  configSecret:
    name: <secret-name>
    existingSecret: true
```

### ✅ Důležité poznámky:

- **Přihlašovací údaje správce MinIO** (`MINIO_ROOT_USER` a `MINIO_ROOT_PASSWORD`)  jsou stále vyžadovány pro počáteční nastavení, i když je OIDC povoleno.
- Ujistěte se, že název Secretu `<secret-name>`) odpovídá hodnotě `configSecret.name` v souboru `values.yaml`.
- Proměnné `HTTP_PROXY` a `NO_PROXY` jsou volitelné. Přidejte je pouze v případě, že váš cluster vyžaduje proxy pro komunikaci s vnějším světem.


## Správa rolí OIDC v MinIO

Při přihlašování do MinIO prostřednictvím e-INFRA CZ SSO narazíte na stránku se souhlasem podobnou této:

![minio-consent](/img/ceritsc/minio-consent.png)

**Je zásadní si poznamenat název role (group)**, který bude použit pro přístupovou politiku v MinIO. V tomto příkladu je role `urn:geant:muni:cz:group:MU:kubernetes-admins@idm.ics.muni.cz`, zvýrazněná červeným obdélníkem výše.


### Krok 1: Přihlaste se jako administrátor

Počáteční přihlášení přes SSO pravděpodobně **selže** kvůli chybějícím politikám založeným na rolích.
Pro pokračování proveďte následující kroky:

1. Na úvodní stránce webové konzole MinIO klikněte na **Other Authentication Methods**.
2. Vyberte možnost **Use Credentials**.
3. Přihlaste se pomocí administrátorských údajů pro MinIO uvedených výše:
   - **Uživatelské jméno:** `<admin-username>`
   - **Heslo:** `<admin-password>`


### Krok 2: Vytvoření politiky pro roli

Přejděte do nabídky **Administrator** → **Policies**  a vytvořte **novou politiku s přesným názvem role**, např. `urn:geant:muni:cz:group:MU:kubernetes-admins@idm.ics.muni.cz`.

V editoru politik definujte politiku podobnou následujícímu JSONu:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:*"
            ],
            "Resource": [
                "arn:aws:s3:::${jwt:preferred_username}-*"
            ]
        },
        {
            "Effect": "Allow",
            "Action": [
                "s3:*"
            ],
            "Resource": [
                "arn:aws:s3:::shared-bucket"
            ]
        }
    ]
}
```

#### ✅ Vysvětlení zásady:
- Tato zásada umožňuje uživatelům se specifickou **OIDC rolí** vytvářet a spravovat buckety jejichž název odpovídá vzoru `<loginname>-něco`.

  Například uživatel s přihlašovacím jménem `xhejtman` může vytvořit bucket s názvem `xhejtman-test`.

- Dále uděluje plný přístup k bucketu `shared-bucket`, který by měl být předem vytvořen administrátorem MinIO.

- Vzhledem k tomu, že tato politika umožňuje i mazání bucketu **zvažte omezení oprávnění** (např. pouze na `s3:PutObject`, `s3:GetObject`) podle vašich bezpečnostních požadavků. Více informací naleznete v [dokumentaci k politikám MinIO](https://min.io/docs/minio/linux/administration/identity-access-management/policy-based-access-control.html).

### 🎯 Závěrečné poznámky:

- **Název politiky musí přesně odpovídat názvu OIDC role**, jinak bude přístup odepřen.
- Různým rolím můžete přiřadit různé politiky a tím řídit přístup s větší mírou podrobnosti.
